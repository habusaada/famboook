# FB-DEVOPS-01 — Isolated Frontend Builds: Runbook

**Status:** implemented in the repository (2026-10-31), NOT applied to Production. The
Production migration (§7) needs the project owner's separate approval. Until then, the
Production unit, its drop-ins and its `.next/<id>` releases stay exactly as they are.

## 1. Why

An isolated build (`FAMBOOOK_NEXT_DIST_DIR`) used to go into `frontend/.next/<id>`. Two
Next.js 16.3.6 behaviours made that unreliable:

| Problem | Cause in Next.js | Effect |
|---|---|---|
| Stale route types fail the build | `tsconfig.json` includes `.next/types/**/*.ts` and `.next/dev/types/**/*.ts`. A build only filters its own `<distDir>/dev/types` (`lib/typescript/runTypeCheck.js`), and only a default build or `next dev` refreshes those folders | An isolated build type-checks an old `validator.ts` that imports removed pages |
| Tracked files edited | Each build appends its own type folders to `tsconfig.json` and rewrites `next-env.d.ts` (`lib/typescript/writeConfigurationDefaults.js`) | A modified checkout, and later builds that check earlier builds' types |
| Releases deleted | A default `next build` empties `.next/` except `cache`, `dev`, `lock` and `trace` (`build/index.js`) | A plain build deletes every `.next/<id>`, including the one being served |

## 2. How it works now

**Location.** Releases are built into `frontend/.builds/<release-id>`. A default build never
touches `.builds/`, and TypeScript's `**` globs skip dot-folders, so the project's
`tsconfig.json` never includes it. `.builds/` is ignored by Git and by ESLint.

**Release id.** `^[a-z0-9][a-z0-9-]{0,39}$`, the same in `frontend/lib/release-dir.ts`
and every script. Absolute paths, `..`, `/`, dots and capitals are refused. Suggested
form: `<date>-<short commit>`, for example `20261031-1c600a2`.

**TypeScript.** `build-frontend.sh` writes `.builds/<id>.tsconfig.json` (next to the release,
because Next.js empties the release folder when the build starts):

```jsonc
// Generated by deploy/scripts/build-frontend.sh for release <id> (FB-DEVOPS-01). Do not edit.
{
  "extends": "../tsconfig.json",
  "include": ["../next-env.d.ts", "../**/*.ts", "../**/*.tsx", "../**/*.mts", "./<id>/types/**/*.ts"],
  "exclude": ["../node_modules"]
}
```

The include list is the project's own, read with TypeScript's parser, minus every entry
under `.next/` or `.builds/`, plus this release's generated types. `next.config.ts` points
`typescript.tsconfigPath` at that file for a `.builds/<id>` build, so Next.js writes any
defaults there and never into the tracked `tsconfig.json`. Strict mode, the route
validator (`<id>/types/validator.ts`) and the build's own type check stay on;
`ignoreBuildErrors` is not used. Next.js may append two non-matching entries to the
generated file; they are harmless.

`next.config.ts` refuses a `.builds/<id>` build whose generated file is missing, so a
release cannot be built, or run under `next dev`, around the script. Serving a release does
not need it.

**`next-env.d.ts`.** Next.js rewrites it (ignored by Git) to import the release's types. The
script restores the previous copy (or removes the file, if there was none) when it finishes,
whatever the outcome, including an interrupt. Only `SIGKILL` can leave it rewritten; the next
`next build` or `next dev` rewrites it again.

**Tracked files.** The script hashes every tracked file that differs from `HEAD` before and
after the build. Earlier local changes are kept and allowed. A change made during the build
fails it, is reported, and is left in place for inspection, never reverted.

**Never deleted, never overwritten.** A release id that already exists, or a leftover
generated tsconfig, is refused. A failed build keeps its folder, marked
`"status": "failed"`, and cannot be smoke-tested or activated. Nothing deletes releases
automatically.

**One build at a time.** `flock` on `.builds/.build.lock`. A second build stops at once.

**Metadata.** `.builds/<id>/famboook-release.json`: release id, status (and reason), commit,
whether the working tree was modified, start and finish times, `BUILD_ID`, Node and Next.js
versions, builder.

## 3. Build, test, switch, roll back

All as the `deploy` user from the repository root unless marked `sudo`.

```bash
# 1. Build (the active release keeps serving).
bash deploy/scripts/build-frontend.sh 20261031-1c600a2

# 2. Smoke-test it on a spare port (default 3901). Starts and stops its own server.
bash deploy/scripts/smoke-frontend-release.sh 20261031-1c600a2 3901

# 3. Switch (after the migration in §7). As an administrator: `deploy` has no sudo password.
sudo bash deploy/scripts/switch-frontend-release.sh 20261031-1c600a2

# Show what is configured, running and previous.
sudo bash deploy/scripts/switch-frontend-release.sh --status

# Roll back to the previous release: no rebuild.
sudo bash deploy/scripts/switch-frontend-release.sh --rollback
```

The smoke test checks `/`, `/welcome`, the `app.famboook.com` root redirect, `/login`,
`/family/login`, `robots.txt`, `sitemap.xml` and the `/verify` `noindex` header.

**The switch refuses, and changes nothing,** when: the release is failed, incomplete or
interrupted (no `"status": "succeeded"`); the unit does not read the environment file; the
file is missing, invalid or sets the variable more than once; the running service has a
different value from the file; or another switch holds the lock.

**State.** Both files are written in full first, then renamed, so a full disk stops the
switch before anything changes.

**Verification.** After restarting, it waits up to 30 seconds for the service to be active,
really running with the new value (read from the process), and answering `/login` with 200.
A failed restart counts as a failed verification.

**A failed switch restores itself:** it puts both files back, restarts the earlier release,
verifies it and exits non-zero. If that fails too it prints `CRITICAL` and the state.

**A failed rollback** does not try a third release: it exits non-zero and prints the state.
A successful rollback swaps the two values, so a second `--rollback` returns forward.

Downtime is a few seconds per restart.

**Compatibility change:** `deploy/scripts/deploy-frontend.sh` no longer runs `npm ci`, a
plain build or a restart. It now takes a release id and calls `build-frontend.sh`. The runbooks
that called it (docs/08, FB-GEO-01, FB-NOTIFY-01, FB-WEB-04) now give these steps.

**What a release does not isolate.** `next start` reads these from the working tree, not from
the release: `public/`, `next.config.ts`, `node_modules` and the `.env*` files.

- `--rollback` restores the build output only. If the commit between the two releases changed
  any of those, roll back that content as well, or fix forward.
- Do not check out a commit older than FB-DEVOPS-01 while a `.builds/<id>` release is
  configured: its `next.config.ts` refuses that value and the service will not start. Switch to a
  legacy `.next/<id>` first, if one still exists.

## 4. Dependencies (shared `node_modules`)

The scripts never run `npm ci`: every release and the running service share
`frontend/node_modules`.

- If `frontend/package-lock.json` is unchanged between the active release's commit (its
  `famboook-release.json`) and the new one, install nothing:
  `git diff --quiet <active-commit> HEAD -- frontend/package-lock.json`.
- If it changed, run `npm ci` in an approved window, as `deploy`, just before the build.
  It replaces packages under the running service, so restart soon after (the switch does).
- Rolling back across a lockfile change also needs the older dependencies: check out that
  lockfile and run `npm ci` again, or treat it as a forward fix.
- Long-term fix: one checkout with its own `node_modules` per release, switched by symlink.
  Not part of this change.

## 5. Retention

No automatic deletion. Keep at least the active and the previous release. Remove an old
release by hand only after `--status` shows it is neither active nor previous, together
with its `.builds/<id>.tsconfig.json`. A release's `cache/` can be removed once it is
superseded.

## 6. Legacy `.next/<id>` releases

`next.config.ts` still accepts `FAMBOOOK_NEXT_DIST_DIR=.next/<id>` so that the current
Production release (`.next/fb-seo-03-04` as reported) and the U4 development server keep
working. Building into it prints a warning.

Once this commit is checked out, a default `next build` refuses to run while any
`.next/<id>/BUILD_ID` exists. The guard does not see a folder without a `BUILD_ID`, such as a
development server's, and it is not on Production until this commit is deployed. **Until the
migration, never run a plain `next build` or `npm run build` on Production**: it deletes every
`.next/<id>`.

## 7. Production migration (planning only, needs approval)

1. Read-only checks: the `.next/*` releases, free disk space, that `flock` exists
   (`util-linux`), and every place that can set the release:

   ```bash
   systemctl cat famboook-frontend                                   # unit and every drop-in, in order
   systemctl show famboook-frontend -p Environment -p EnvironmentFiles -p ExecStart -p DropInPaths
   sudo tr '\0' '\n' </proc/"$(systemctl show -p MainPID --value famboook-frontend)"/environ | grep FAMBOOOK
   ```

   The repository documents only `10-bind-localhost.conf` (read 2026-10-30), not how Production
   sets `FAMBOOOK_NEXT_DIST_DIR`. Decide from the real output:

   | Where the value is set | Decision |
   |---|---|
   | An `Environment=` line | `systemd.exec(5)` says an environment file overrides it. Prove that on this host with the command below, and the switch proves it again for this unit |
   | Inside `ExecStart=`, a wrapper script or `env VAR=…` | **Stop.** The file cannot win; this needs its own approved unit change |
   | Another `EnvironmentFile=` listed after ours | **Stop.** The later file wins; merge them in an approved change |
   | Only in a frontend `.env*` file | The process environment wins over it, so the file takes effect; remove the old line later |

   A transient unit proves the `Environment=` case on this systemd version without touching
   `famboook-frontend` (expected output: `.builds/from-file`):

   ```bash
   f=$(mktemp); echo 'FAMBOOOK_NEXT_DIST_DIR=.builds/from-file' >"$f"
   sudo systemd-run --wait --pipe --quiet -p Environment=FAMBOOOK_NEXT_DIST_DIR=.next/from-environment \
     -p EnvironmentFile="$f" /usr/bin/printenv FAMBOOOK_NEXT_DIST_DIR
   rm -f "$f"
   ```
2. Deploy this commit with `git pull --ff-only` as `deploy`. Nothing is built or restarted.
3. Build the first release into `.builds/<id>` and smoke-test it on a spare port.
4. As root, create `/etc/famboook/frontend-release.env` holding the **current** value (for
   example `FAMBOOOK_NEXT_DIST_DIR=.next/fb-seo-03-04`), install
   `deploy/systemd/famboook-frontend.service.d/20-release.conf`, run `systemctl daemon-reload`
   and restart. The site keeps serving the same release, now through the file. Create the file
   first: without it the service will not start. This restart cannot show which setting
   won, because both hold the same value.
5. Confirm with `--status`, then switch with the switch script. This is the real proof: if
   the file does not control the service, verification sees the old value and the switch
   restores itself.
6. Remove any old `Environment=FAMBOOOK_NEXT_DIST_DIR=` line only in a later, approved change.
7. Keep the legacy `.next/<id>` releases until the new path has been proven.

**Undoing the migration:** remove the drop-in, `systemctl daemon-reload`, restart. The unit
then serves whatever it served before step 4.

Unit and environment templates: `deploy/systemd/famboook-frontend.service`,
`deploy/systemd/famboook-frontend.service.d/20-release.conf`,
`deploy/env/frontend-release.env.example`.

## 8. Tests and CI

- `frontend/tests/next-config-release-dir.test.ts`: release ids, unsafe values, the
  TypeScript configuration choice, legacy directories.
- `deploy/tests/build-frontend.test.sh`: the build script against a fake `next` in a throwaway
  repository (ids, root, missing settings, metadata, existing releases, failures, interrupts,
  tracked changes, earlier local changes, the lock where `flock` exists), Git ignore checks,
  smoke arguments, and the switch script's decisions against a **fake** `systemctl`, `curl`
  and `/proc`. The switch has never run against real systemd.
- `deploy/tests/build-frontend-integration.sh` (`FAMBOOOK_BUILD_INTEGRATION=1`): real builds
  with planted stale types, a planted type error, a smoke test, a default build refused beside
  a legacy release, and a default build beside `.builds/` (skipped if `.next/` holds a folder
  that is not Next.js's own, which that build would delete).
- `.github/workflows/frontend.yml`: `npm ci`, typegen, type check, lint, tests, build,
  shellcheck (warnings and above), the systemd precedence probe and both script suites on Ubuntu
  with Node 24, where a skipped test fails the run (`FAMBOOOK_TESTS_NO_SKIP=1`). It runs on
  pushes to `main`, `feature/**` and `release/**`, and on pull requests. No secrets, no deployment.
