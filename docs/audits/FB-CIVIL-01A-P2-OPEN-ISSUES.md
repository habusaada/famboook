# FB-CIVIL-01A-P2 — Open Issues and Decisions

**Status:** P2 is complete on the disposable test cluster with synthetic data.

**Blocking:** none of these items blocks P2. **None may be resolved by starting P3, publishing, or loading real data without a new explicit approval.** The P1 open issues still apply, especially P1-OI-01, P1-OI-02 and P1-OI-03.

| ID | Item | Type | Needed before | Recommendation |
|---|---|---|---|---|
| **P2-OI-01** | **Who logs in to run the loader.** The loader accepts any login that can `SET ROLE famboook_identity_writer`, superusers included (it then has writer privileges). | Operations / security | Any non-local use | A dedicated `NOINHERIT` login that is a member of the writer role only, created by a DBA with an interactive password. Never a superuser or the application login. |
| **P2-OI-02** | **Server log leakage.** A failed COPY makes PostgreSQL log `CONTEXT: COPY rows, line N: "<record>"`, which contains record text. Application-side redaction cannot prevent this. | Security configuration | Any real data | DBA configuration for the import login before real data, for example `ALTER ROLE <import login> SET log_min_messages = 'panic'` and `SET log_min_error_statement = 'panic'`, plus restricted log access. Confirm on the target server. Extends P1-OI-03. |
| **P2-OI-03** | **Backups and UNLOGGED staging.** Staging is UNLOGGED (no WAL; emptied after a server crash; not on streaming replicas), but `pg_dump` still includes UNLOGGED data unless `--no-unlogged-table-data` is passed. | Decision / operations | Any real data | Add `--no-unlogged-table-data` to the backup command, or never take a backup while real data is staged. Purge staging promptly (P2-OI-04). |
| **P2-OI-04** | **Staging retention.** <ul><li>Rejected or aborted runs are purged immediately.</li><li>A completed staging awaits P3 while its run stays RUNNING, which blocks any new run (by design).</li><li>There is no time-based expiry.</li></ul> | Decision | P3 | P3 must purge staging in the same procedure that publishes. Set a maximum time staged real data may wait, for example 24 h; after that, abort. |
| **P2-OI-05** | **NULL vs empty string.** The loader keeps the only distinction CSV can carry: an unquoted empty field becomes JSON `null`, and a quoted `""` becomes `""`. The real export probably writes every empty value unquoted, so all empties would become `null`. P0 noted the manifest says "empty may be NULL or empty string". | Decision (OD-04) | P3 diff design | Confirm with the source owner. P3's blank-value policy should treat `null` and `""` as one "blank" unless the source owner says otherwise. |

| **P2-OI-08** | **P1 schema hardened during P2.** <ul><li>`import_files.loaded_rows` is now `NOT NULL DEFAULT 0` (it was nullable, so `loaded_rows + n` stayed NULL).</li><li>The VERIFIED/STAGED checks are now NULL-safe; previously a NULL let the CHECK pass.</li><li>Found by the P2 tests.</li><li>The file `01-schema.sql` is uncommitted and has never been applied outside the test cluster, so no migration of existing data is needed.</li></ul> | Review | P1/P2 review | Reviewer acknowledgement. ## Documentation conflicts

None found. Two points still need reviewer acknowledgement:
- **Staging location:** the staging schema follows the P1 approach (an owner-applied SQL script, not a Laravel migration). It adds a separate schema `identity_ref_staging` instead of the per-run `staging_<run>` table proposed in the technical design. That keeps the writer without DDL rights, which the P1 security posture requires.
- **Run status after staging:** P2 leaves the run RUNNING after staging, which differs from the workflow outline's "drop staging, close the run". Publication and closure belong to P3, as this phase's brief requires.
